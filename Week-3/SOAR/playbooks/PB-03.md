# PB-03 — Web / XSS

**Alert rules:** `SIEM_WEB_001_HIGH_RATE_HTTP_REQUESTS` + `SIEM_WEB_004_XSS_ATTACK_DETECTED`
**Source:** SIEM06/SIEM07 receivers
**Tier max:** Tier 1 (propose only, WAF-review only)

## What the evidence proves
- XSS 004: one verified transaction (`ZwuU-873D9JP20xgx6@OtgAAAAA`) from `192.168.171.129`
  to `/index.php?p=...<script>...alert(1)...`, HTTP 500.
- HTTP 001: high-rate requests from one source against threshold 80.

## What the evidence does NOT prove
- Browser-side JavaScript execution.
- Session compromise.
- That the HTTP 001 source group joins exactly to the saved firing trigger
  (**Week-2 acceptance gate 2 — still open**).

## Automated (Tier 0)
Parse → extract IOCs → enrich (stub) → create ticket → notify → audit.

## Proposed (Tier 1, needs analyst)
- `propose_waf_rule_review`: "Propose WAF rule review for `{request_uri}` (NOT executed)"

## Prohibited (Tier 2)
- `execute_rate_limit` — HTTP correlation gap; cannot block source on unproven join.
- `execute_isolation`, `disable_account` — Week-2 reports prohibit automatic action.

## Why no source-block proposal?
The HTTP 001 correlation gap (Week-2 acceptance gate 2) means the row-level join between
the saved firing trigger and the high-rate source group is unproven. Blocking on it would
automate on an unverified detection. WAF-rule review is safe because it changes nothing
until a human applies the rule.
