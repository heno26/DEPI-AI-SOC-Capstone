# Week-3 SOAR Evidence

## 1. Purpose

This directory documents the tickets, audit logs, and screenshots produced by the Week-3
SOAR dispatcher from real Week-2 evidence. It mirrors the discipline of
`Week-2/Evidence/SIEM-OpenObserve/README.md`: every artefact is traceable to its source,
every claim is stated plainly, and pending items are labelled as such.

**Important:** A generated ticket or a successful dispatch does not automatically establish
that an analyst has reviewed it, that any action was taken, or that any Week-2 acceptance
gate has been resolved.

## 6. What is NOT in this evidence

- No executed remediation. No firewall rule was changed. No host was isolated. No account
  was locked. This is by design.
- No live SIEM call. The evidence JSON was read from disk; no OpenObserve instance was
  queried during dispatch.
- No fresh AI output. The `ai_triage` field in every ticket is the Week-2 output, copied
  unchanged.
- No analyst decisions. Every ticket has `review_status = "Pending Review"` and
  `analyst_decision = null`.
- No live TheHive ticket. The `thehive_stub.py` backend is documented but not implemented.

These absences are the honesty boundary. A reader of this evidence folder should not infer
from the presence of a ticket that any action occurred.

## 7. Integrity verification

To verify ticket integrity after a fresh clone:

```powershell
Get-FileHash Week-3/SOAR/tickets/*.json -Algorithm SHA256
```

To regenerate the tickets from source evidence (idempotent):

```powershell
Remove-Item Week-3/SOAR/tickets/*.json
Remove-Item Week-3/SOAR/audit/*.jsonl
python -B Week-3/SOAR/dispatcher.py --evidence Week-2/Evidence/SIEM-OpenObserve --playbooks Week-3/SOAR/playbooks --out Week-3/SOAR
```

The regenerated tickets should be identical (same `event_id`, same content) except for
`created_at_utc` timestamp.
